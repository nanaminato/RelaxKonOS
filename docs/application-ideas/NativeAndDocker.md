# 直接安装与 Docker 部署的统一设计建议

> 状态：规划，未实施或验收。更新：2026-11-04。产品约束：Windows 直接安装；Linux 按应用、实例及实际支持能力选择直接安装或 Docker。本文拥有跨应用方案讨论；正式实施需同步对应领域设计、协议、组件目录和验证记录。

[返回总览](README.md) · [数据库引擎管理](proposals/DatabaseManagement.md)

## 1. 当前基础与差距

- `IWebServerManager`、`IWebServerProvider` 已按实例 ID 调用，适合继续承载多个运行实例。
- `NginxWebServerManager` 的执行、配置检查、证书路径和静态目录检查仍基于宿主环境；固定受管根目录及部分静态锁不适合直接扩展为任意多实例。
- [组件目录](../platform/RelaxKonOS.ComponentCatalog.Design.md)当前封闭机制为 apt/archive/download/roapp，尚无容器安装 provider；不能仅添加 JSON 就声称支持 Docker。
- [应用部署](../applications/RelaxKonOS.ApplicationDeployment.Design.md)已有镜像身份、修订、操作及秘密基础，但当前仅支持受管命名卷，不支持任意宿主挂载，通用部署回滚也不负责数据库数据迁移。
- 现有宿主 Nginx 验证证据不覆盖容器配置、证书轮换、容器网络或镜像更新。

## 2. 分开表达的维度

| 维度 | 示例 | 作用 |
| --- | --- | --- |
| 产品 | nginx、mysql、postgresql | 选择业务语义和原生配置适配器 |
| 部署方式 | native、docker | 选择执行环境和生命周期后端 |
| 安装机制 | apt、官方归档/安装器、容器镜像 | 选择具体制品和事务机制 |
| 所有权 | Managed、Integrated | 区分平台拥有与授权集成的资源 |
| 实例身份 | 稳定 instanceId | 关联站点、账号、证书、数据与操作 |
| 运行绑定 | 服务身份或 containerId/imageId | 描述当前实际运行资源，可随更新替换 |

不要把 Docker 加入现有 `Managed/Integrated` 枚举：外部容器可以是 Integrated，平台创建的容器可以是 Managed。稳定实例 ID 不等于容器名称或容器 ID。

程序安装与实例分别记录，允许未来多个宿主实例共享程序安装，多个容器实例共享镜像；卸载共享程序/清理镜像前核对引用。首个切片可以限制数量，但不能用全局“nginx 已安装”替代实例状态。

安装方式由目标 Server 的 OS 和能力决定，不由桌面客户端 OS 决定。Docker 未就绪时显示原因与组件中心跳转，不静默改成直接安装；Windows 不展示 Docker 选项。

## 3. 复用领域能力，替换运行后端

建议职责关系：业务管理入口 → 产品领域适配器 → 直接安装或 Docker 后端 → 已有服务/Helper/Docker 执行能力。

Nginx 的站点、域名、反向代理和证书绑定仍由 Web Server 领域拥有。宿主后端负责本机程序、服务及路径；Docker 后端负责容器执行、卷内容发布、信号、日志及映射。数据库账号、改密、恢复和数据升级仍由数据库领域拥有，不能下沉为通用容器环境变量编辑。

Docker 领域唯一拥有 Engine 交互与容器资源执行。领域协调器通过类型化端口使用它，不另起 Docker CLI 执行器。不在每个应用里复制拉镜像、重建和恢复逻辑，也不把所有产品逻辑塞进一个万能安装器。

容器部署事务优先复用已有应用部署原语；可建立受领域委托控制的部署记录，固定实例到部署的关联。Web Server 或数据库拥有业务期望，部署执行器拥有容器操作回执，两者通过修订和操作 ID 关联。一个受管实例不能同时被两个独立协调器修改；Docker 管理器对领域拥有资源展示所属应用并跳转，外部漂移须核对后再接受变更。

## 4. 组件中心与能力模型

组件中心在产品下展示实例和安装方式，而不是建立互不相关的“宿主 Nginx 应用”和“Docker Nginx 应用”。业务页面可直接打开预填方案的组件中心。

目录目标需要新增明确的部署选项身份及安装机制匹配，允许同一 Linux OS/架构有 native/docker 两个有效选项，不能按 OS 取第一个。Docker Engine、架构、权限、网络和资源条件进入预检。

新容器 provider 必须为宿主编译注册、独立授权的能力。清单不能自行授予 Docker socket、任意 bind mount、特权模式或 shell 权限。冻结发布者/仓库、tag 展示值、实际不可变镜像身份、平台、配置与状态修订；不能执行时重新拉 latest。

能力按实例返回：站点管理、TLS、重载、静态文件、账号管理、忘记密码恢复、数据迁移等。外部集成或未验收模式可只读，不能因为引擎名称相同就显示全部动作。

## 5. Nginx 需要改进的关键点

### 5.1 配置与文件

把配置生成与执行环境分开。站点模型保存逻辑资源引用，后端生成宿主或容器可见路径，不能把宿主证书路径直接写进容器配置。静态目录用受授权资源映射，分别记录源位置、目标路径和读写权限。

首版优先受管卷与固定目录布局，通过受控文件传输发布配置和证书，避免直接开放任意宿主挂载。若需要专用 bind mount，必须作为独立范围明确的能力实现和验证，不能绕开现有应用部署限制。Nginx 配置、证书和静态内容尽量只读，缓存和临时文件单独可写。

候选配置以完整修订生成，在匹配镜像、完整证书/文件映射和目标网络中执行原生配置检查。必要时在实际目标容器重复检查；成功后原子发布配置，重载并检查实际服务。失败恢复原修订并核实，不以命令退出码代替生效结果。

目录级映射或可验证的卷内发布应保证证书/配置替换可见；单文件 bind mount 需要验证文件替换后容器是否仍引用旧对象。

### 5.2 证书与 ACME

证书权威仍在证书领域；只向绑定实例投放所需证书材料，不挂整个证书库。记录实例、证书修订和部署结果，续期后触发重新投放、检查、重载与 TLS 实测。部分失败按实例记录。

HTTP-01 验证要把公网域名/80 端口、实际入口 Nginx、挑战目录及容器映射连起来；不能假设宿主路径容器可见。多个 Nginx 并存时明确哪个入口负责挑战路由，不能给每个容器争抢宿主 80。

### 5.3 网络与上游

| Nginx 位置 | 后端位置 | 推荐连接方式 |
| --- | --- | --- |
| 宿主 | 宿主 | 明确宿主地址与端口 |
| 宿主 | 容器 | 显式绑定的宿主发布端口 |
| 容器 | 同机容器 | 授权加入同一用户定义网络，使用服务名与容器端口 |
| 容器 | 宿主 | 明确宿主可达地址/网关映射及监听策略 |
| 任意 | 其他主机 | 经过验证的远端地址、VPN 或隧道 |

容器内的 127.0.0.1 指向容器自身。上游模型应保存应用/服务端点引用及网络上下文，不能只保存全局 localhost URL，也不能固化短生命周期容器 IP。服务名解析与后端重建后的重新解析策略需要按 Nginx 版本验证。

外部监听与内部监听分别建模：宿主地址:端口 → 容器端口；同一地址上的端口不能冲突。多个实例可使用不同端口/IP，由一个入口 Nginx 转发，不能让所有实例默认发布 80/443。

### 5.4 生命周期

容器 Nginx 在容器内检查并通过可信 Engine 操作发送信号/执行固定动作，不调用宿主 systemctl。更新替换运行绑定，保持稳定实例、站点和卷引用；相同宿主端口下首版可接受受控停机，不能承诺自动零停机。

只有数据/配置格式允许时才提供回退。外部容器发现仅为候选，确认集成时检查实际镜像、命令、挂载、写入范围和重载能力，不凭标签自动接管。

## 6. 数据库 Docker 模式的区别

安装镜像与创建实例分开；持久数据留在明确归属的卷中，删除容器不删除数据。初始化凭据仅供首次初始化；已存在 MySQL 数据目录时修改 MYSQL_ROOT_PASSWORD 环境变量不会重置现有密码。

正常改密通过数据库认证通道执行；管理员遗失密码的恢复要核对实例、卷、容器与镜像身份，独占数据卷，隔离网络后走引擎专属流程。不能启动第二个数据库进程同时写原卷。

镜像版本回退不撤销数据格式升级，数据库主版本升级使用备份/迁移专属流程。对外端口默认不发布或明确绑定本机，选择外部访问时同时核对认证和实际网络访问策略。

## 7. 网络控制必须覆盖 Docker 路径

Docker 发布端口的流量路径可能绕过 UFW 常规规则，因此不能复用“UFW 已拒绝”作为容器不对外的证明。网络适配器要识别实际 Docker 防火墙后端、IPv4/IPv6、发布绑定和路由路径。

限制来源的规则必须落在实际受支持并验收的 Docker 流量控制点，不能跨 iptables/nftables 盲写同一规则。无法落实时明确不支持该策略，可选择不发布、回环绑定或受控组网路径。外部探测分别验证允许与拒绝来源，保留未知状态。

## 8. 方式切换与用户流程

安装方式是实例创建选择，native → docker 或反向切换是迁移计划，不是设置页的即时开关。建立目标、复制或转换数据/配置、验证、人工切换入口，再保留或移除源；跨实例证书、站点和业务数据分别处理。

建议页面：产品列表 → 实例卡片（部署方式、所有权、状态、端点）→ 业务管理。创建时 Windows 直接进入直接安装方案，Linux 显示当前支持的两种方案及所需依赖。高级设置按资源、存储、网络、版本、备份展开，业务界面不要求用户手写 Compose。

| 编号 | 状态 | 范围 |
| --- | --- | --- |
| ND-01 | 待实施 | 实例/安装/运行绑定与能力契约，目录多部署选项，按目标主机平台过滤 |
| ND-02 | 待实施 | Nginx 宿主实现解耦执行环境，原直接安装功能回归及实例级锁 |
| ND-03 | 待实施 | 容器部署 provider、Docker 唯一执行权威、镜像信任/冻结、卷与资源所有权 |
| ND-04 | 待实施 | 容器 Nginx 配置、静态文件、证书部署、ACME 与网络上游 |
| ND-05 | 待实施 | 数据库双模式、正常改密与隔离恢复，关联 DB-01～07 |
| ND-06 | 待实施 | Windows 直接安装和 Linux 两模式的真实安装/跨版本/修复/保留数据卸载/失败恢复矩阵 |
| ND-07 | 后续 | 多实例拓扑、外部容器集成、方式迁移及更多产品适配 |

优先 Nginx 宿主解耦与容器最小闭环，再复用后端能力接数据库；也可先用数据库验证持久卷，但两者的领域验收不能互相替代。远程 Engine、Windows 容器、任意 Compose 导入和任意挂载不随本方案自动开放。

验收包含宿主与容器并存、端口冲突、证书续期、容器后端重建、Docker 不可用、外部漂移、配置发布中断、原操作核对、实际外网访问限制及卷保留。管理模块休眠不停止已部署服务；进行中的领域任务在真实完成或可靠交接前持有租约。不得把镜像拉取成功或容器 running 作为业务健康证明。

API/清单演进直接升级唯一当前契约，同步所有客户端、Server、Helper、目录、测试、示例与正式文档，不保留旧路由或双格式回退。
