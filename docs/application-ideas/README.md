## 筛选原则

核心问题是：用户已经在 RelaxKonOS 管理服务器，新功能能否让他少切工具、少重复连接配置，并更容易完成一件完整的事？

- 优先复用成熟外部工具的引擎或界面，原生部分负责上下文关联、任务管理与跨模块流程。
- 优先支持服务端持续执行、跨设备查看、复用应用/目录/域名/主机上下文的场景。
- 只有启停和网页链接的功能通常采用部署模板，不单独重做原生管理界面。
- 单纯建表、删表、SQL 查询不优先；应用建库、备份恢复、迁移和连接诊断更有集成价值。
- 外部工具的许可、维护状况、接口、资源消耗和平台支持在立项时重新核实。本文提及的工具均为待评估选项。

## 形态约定

| 形态 | 适用情况 |
| --- | --- |
| 原生应用 | 有独立工作流程，需要跨多个领域协作 |
| 外部适配 | 成熟引擎负责执行，RelaxKonOS 提供管理入口 |
| 现有扩展 | 与已有应用强关联，放在原入口更自然 |
| 部署模板 | 主要使用外部产品界面，平台提供部署和运维关联 |

## 维护规则

1. 新候选在 [Catalog.md](Catalog.md) 末尾追加编号，从 `APP-061` 起；已有编号保持稳定，撤回项保留记录。
2. 初始状态为“候选”；需要深入讨论时，复制模板到 `proposals/`，并在清单与方案索引添加链接。
3. 推荐顺序集中维护在 [Priorities.md](Priorities.md)，候选编号不表示实施顺序。
4. 立项后链接到拥有该领域的正式设计与跟踪项。本目录保留需求动机和决策记录，实施细节及验证状态由正式文档维护。
5. 已存在基础能力的候选，应先核对现有实现，明确新增范围，避免建立第二套执行器、调度器或状态权威。

可使用状态：候选、评估中、已立项、暂缓、撤回、已转入正式文档。状态变化应附日期与原因；“已立项”不代表已实现。

## 与现有架构和文档的关系

- 模块边界和休眠遵循[模块边界设计](../architecture/RelaxKonOS.ServerModuleBoundaries.Design.md)与[驻留设计](../architecture/RelaxKonOS.ServerModuleResidency.Design.md)。管理模块休眠不等于停止外部服务或取消后台承诺。
- 外部软件的安装、更新、修复、回退、卸载及来源管理遵循[受管运行时设计](../platform/RelaxKonOS.ManagedRuntimes.Design.md)，统一入口复用[组件中心](../platform/RelaxKonOS.ComponentCenter.Design.md)。本目录不新增安装授权或生命周期实现承诺。
- 编排能力复用[任务编排设计](../platform/RelaxKonOS.TaskOrchestration.Design.md)，不把任意命令执行当成所有应用的通用实现方式。
- Android 专属交互、布局、适配及进度文档由 [Android 文档目录](../../Client/RelaxKonOS.Client.Android/docs/README.md)拥有，本目录只讨论跨端产品方向。
- 功能模块、客户端应用与外部运行时是不同对象；模块拆分不能消除外部服务自身的资源成本。
