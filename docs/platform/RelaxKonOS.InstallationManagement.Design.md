# 安装组件、设置与修复

更新日期：2026-10-25。服务器中心安装管理的实施规范；Android 页面细节由 Android 自有文档维护。

组件中心的统一入口设计见[组件中心](RelaxKonOS.ComponentCenter.Design.md)。其 CC-07 仅聚合自身组件的状态与维护入口；Server/Guardian/Helper 的部署、升级和修复仍由本文及服务器中心负责，不能依赖正在替换的 Server 执行自身升级。该聚合尚未实施。

## 产品入口

管理安装分为详情、组件、安装设置和维护。首次安装提供 Guardian 可选项；后续在组件页补装或移除。进程守护应用的未安装状态链接到组件管理，同一个部署流程处理两个入口。

桌面服务器中心的 SSH 系统安装向导不再要求选择文件范围或填写白名单，WindowsSystem / LinuxSystem 默认管理所有本地文件。Linux 向安装器同时提交手动授权、宿主管理员和 root 三类 `full` 策略，Windows 提交本地磁盘 `full` 策略；自动模式预检最终选择系统安装时也采用该设置。确认页显示全部本地文件及身份权限说明。普通操作继续遵循登录用户的 OS 权限，特权操作继续校验现有授权来源，不因扩大路径范围而跳过认证。LinuxUser 与 WindowsUser 保留原有用户模式权限策略；维护页及命令行仍可显式配置受限范围。

WindowsSystem、LinuxSystem 和 LinuxUser 支持 Guardian；WindowsUser 当前不支持，界面不得提供不可执行选项。发布包继续携带同版本 Guardian 文件，选择决定是否部署与启动，不决定包内文件是否存在。

## 状态与操作

安装记录保存 guardianEnabled，升级与普通修复继承已有选择。显式配置操作修改选择；未安装、停止、故障和未知必须区分。实际服务列表依据安装记录返回，能力矩阵只描述支持范围。

配置通过现有固定 SSH / 本地提权部署通道执行，必须校验安装 ID、获取独占锁并保存操作记录。配置不下载新版本；补装使用当前版本文件。移除前确认工作负载将停止，定义和日志默认保留。

普通修复恢复所选组件，不隐式补装未选 Guardian，不更改监听地址、权限和证书身份。重新生成证书是显式高级修复动作。

## 安装设置

安装设置支持监听端口、本机 / 局域网访问、Guardian 选择、系统模式文件访问策略与白名单，以及可核实的自动启动选择。设置先读取宿主记录，不用 UI 默认值覆盖未知信息；白名单从受保护的 Helper 策略读取，读取失败不允许保存该策略。目录迁移和安装模式转换使用专门流程。

系统模式自动启动决定服务是否随系统启动，不停止本次正在运行的 Server；Windows 个人模式控制当前用户登录启动。PrivilegedHelper 保持系统服务可用。Linux User 不提供系统级自动启动和系统文件权限编辑。

防火墙添加和移除使用独立 `firewall` 动作，校验安装 ID、锁和回执，不重启 Server。只操作可证明属于安装器的规则：Windows 精确名称与 Group、UFW/iptables/nft 的受管标记、firewalld 的受保护 rich-rule 所有权记录。既有 firewalld 无标记端口规则不被认领或删除；不启用宿主防火墙。更改端口后显式移除旧受管规则，再为新端口添加。

配置提交显示当前值与目标值以及重启影响。配置变更失败应恢复原配置；不得在实际验证前发布新安装状态。网络或证书变化后重新核对连接地址和证书信任。

## 修复验收

修复展示涉及组件与重启影响。分别验证 Server 健康及所选 Guardian 的运行 / 认证 IPC；Server HTTP 健康不能代替 Guardian 健康。Linux User 同时核验私有控制 socket 和 TCP 健康。保留 JWT、审计身份、Guardian 定义和日志。

不提供 ZIP 时重新应用已部署服务与配置；提供 ZIP 时恢复程序文件。包必须匹配当前版本、运行架构和安装模式，恢复前校验完整文件清单及哈希，只复制声明的程序文件，不遍历持久数据链接。桌面本地入口流式上传本地 ZIP，SSH / Android 接收宿主上的 ZIP 绝对路径。版本不匹配或清单损坏拒绝执行，不隐式升级。当前不提供自动逐文件诊断或目录迁移。

## 实施检查

- 首次不选 Guardian，Server 正常运行且不启动 Guardian。
- 补装后 IPC 可用；移除停止工作负载并保留定义。
- 升级、修复及回滚保持组件选择。
- 设置读取失败禁止保存；安装 ID 变化禁止旧窗口写入。
- 网络配置失败恢复原监听配置和运行状态。
- WindowsUser 不显示 Guardian；LinuxUser 不承诺系统级开机启动。

实施进展和未完成验收必须单独记录，不将本规范视为已实现证明。

## 当前实施范围与验证

当前代码已接入上述组件、安装设置、独立防火墙和同版本包修复入口，覆盖桌面本地管理 / SSH 管理 / Android 维护。共享请求包含 `configure`、`firewall`、可空 `guardianEnabled` / `autoStart`：null 保留选择，false 跳过、移除或禁用启动。宿主快照分别返回选择和进程运行状态；进程运行状态不等同于认证 IPC 健康。

安装记录必须显式保存组件选择；缺少该字段时不猜测为已选择，也不通过旧格式解析或迁移适配继续维护。预发布旧记录需按当前安装契约重新部署；Linux 记录丢失时可从可信宿主配置恢复选择。

部署成功时对所选 Guardian 执行宿主本地 `guardian-health` 认证 IPC 检查。配置失败恢复原监听地址、启动选择、组件选择与文件白名单，恢复核验失败明确要求处理，不发布目标状态。

受控验证包括协议序列化、Linux 参数映射、Windows 注册 / 移除分支、三种模式配置失败恢复、跳过 Guardian 的安装记录恢复、本地配置提交前状态复核、桌面视图回归、Guardian IPC 读取及 Android 维护契约测试。桌面 / Server / Android 构建已通过；图像编解码已迁至 SkiaSharp，Server 不再残留 ImageSharp 依赖告警。

2026-10-14 在用户授权的 Debian 13 x64 主机验证：系统模式跳过 Guardian、补装认证 IPC、以普通 UID 运行工作负载、移除停止工作负载并保留定义、升级与普通修复保持选择、同版本 ZIP 恢复损坏 DLL；端口冲突后的监听、自动启动、组件与白名单恢复；独立 nft 删除仅移除受管规则且保留另一规则。通过 nanami 的 SSH 会话验证 Linux User 首次安装、Guardian 配置、连续维护与同版本程序恢复。测试使用独立业务数据目录，没有移除旧业务数据。

Linux User 的 TCP 与私有 socket 均通过真实检查，LAN 配置后从开发机访问受保护 API 得到预期的认证要求；本机健康端点保持仅 loopback 可访问。最终测试版本为 `0.1.0-dev20261014-05`。系统模式 DLL 再次恢复后核对监听、组件、启动、权限设置、JWT / 审计身份以及 Guardian 定义保持不变。Linux 专用锁和数据链接恢复回归测试在主机通过。

真实 Windows 系统 / 个人模式、宿主重启后自动启动以及完整客户端登录重连仍需独立验收。该测试机 root SSH 登录关闭、nanami 没有 sudo 权限；系统模式通过已授权的 `su` 管理会话运行固定启动器，普通用户模式使用 nanami SSH，未声称桌面系统模式 SSH 提权链路已验收。Windows 个人模式不支持 Guardian。Linux User 发布包包含 Server 与 Guardian，不包含系统 Helper。


## 发布包完整性问题（2026-10-24）

已复现本地 `RelaxKonOS-0.1.3-linux-x64-server.zip` 在更新准备阶段被拒绝：归档中没有 `deployment/user/relaxkon`，属于不完整的当前服务器发布包。Linux 系统与用户模式共用服务器发布包，因此系统模式也要求携带此入口；不得删除校验或对旧布局增加兼容分支。应使用当前打包脚本重新构建完整发布包，不向旧版本归档混入其他修订的脚本。

修复跟踪：Linux 启动器对缺少必需组件返回明确的重新打包提示，详细缺失路径保留在操作诊断；PowerShell 与 Bash 打包入口在生成清单和归档之前检查必需入口，防止遗漏用户模式目录后仍成功输出发布物。`package_source_checks.py` 与 `release_inventory_checks.py` 共 23 项通过，包含缺失用户入口的启动器拒绝与两个打包入口的回归检查。该证据仅覆盖包准备，不代表已在用户服务器完成升级。

## 运行版本与发布版本一致性（2026-10-24）

Debian 13 实机发现 0.1.4 已发布、Helper 已更新，但 Server/Guardian 的遗留 systemd drop-in 将 ExecStart 固定在旧的 gitfix 目录。旧 Server 与新 Helper 的用户执行协议版本不同，目录列表和快捷位置请求被拒绝。0.1.4 包内 Server、Guardian、Helper 的协议程序集 SHA-256 一致，安装目录也匹配发布包。

已备份并移走两份旧启动覆盖，重载 systemd 后重启所选服务，确认实际进程路径均为 0.1.4；nanami 登录、根目录/家目录/文档列表和七个快捷位置恢复，Server HTTP 与 Guardian 认证 IPC 健康通过。独立临时目录中真实身份解压 100 个小文件约 2.87 秒，RoyalTerminal-main.zip 的 718 项约 3.07 秒，测试目录已清理，原包未改动。这是单台主机的验收时间，不作为跨平台性能保证。

后续系统模式部署的健康检查同时读取 systemd MainPID 和 `/proc/<pid>/exe`，核对实际 Server 与所选 Guardian 的可执行文件属于目标发布版本。即使旧进程的 HTTP 健康正常，也不能发布成功状态；错误说明要求检查 ExecStart/WorkingDirectory 覆盖。不会自动删除用户自定义 drop-in，也不保留旧协议兼容解析。新增 6 项路径核验回归、原有 2 项配置失败恢复检查及 Bash 语法检查通过。此脚本改动在仓库，已发布的 0.1.4 归档保持原样。

### Windows 运行版本核验

系统模式的安装引擎在启动服务后，以及 bootstrap 的 HTTP 健康检查通过后，均核验 Server、特权 Helper 和已选择的 Guardian。共享脚本 `deployment/windows/RelaxKonOSDeploymentVerification.ps1` 读取 `Win32_Service.PathName` 与服务 PID 对应的 `Win32_Process.ExecutablePath`，要求配置与实际进程均指向目标版本目录。带空格的服务执行路径必须引用；路径不可读、进程缺失、服务在核验期间切换 PID 均失败，不以 HTTP 健康替代版本一致性。失败沿用已有升级回退和配置恢复流程。

个人模式核对 `runtime.json` 的目标执行路径、PID、实际进程路径和启动时间，防止旧记录、旧版本或 PID 复用。独立启动命令不再直接复用仍在运行的其他版本；正常部署先安全停止已记录的旧实例再启动目标版本。个人 Helper 的配置和实际进程由现有 UAC 管理员安装步骤核验，检查失败进入现有 Helper 恢复分支，个人 Server 不因此提权。日期核验同时适用于 PowerShell 5.1 的 JSON 字符串和 PowerShell 7 的 DateTime 值。

Windows Server 发布包必须携带共享核验脚本；打包缺失时拒绝生成发布物。bootstrap 保留 UTF-8 BOM，确保 PowerShell 5.1 正确解析多语言文本。28 项受控核验在 PowerShell 5.1 与 7 均通过，覆盖三个服务的新旧配置/进程、未选择 Guardian、PID 变化、个人实例复用、健康接口正常但版本错误和脚本缺失。原有个人启动、Guardian 选择/配置恢复及证书升级检查通过。没有对本机服务做安装或重启；真实 Windows 系统与个人模式的升级/修复/回滚仍需部署验收。后续重新打包才会包含这些检查，不改写已有发布归档。
