## 1. 职责与文档边界

组件中心是系统内置管理入口，不是新的安装后端。原 TaskOrchestration 中的 Component Installer / Workloads 产品设计由本文拥有。

- 本文拥有组件目录、应用可用性、来源选择、生命周期交互、批量变更和交付跟踪。
- [TaskOrchestration](RelaxKonOS.TaskOrchestration.Design.md) 拥有冻结计划、审批、执行、恢复和审计。
- [ManagedRuntimes](RelaxKonOS.ManagedRuntimes.Design.md) 拥有版本、信任、所有权和领域生命周期事务。
- [InstallationManagement](RelaxKonOS.InstallationManagement.Design.md) 继续拥有 RelaxKonOS 自身部署与维护，组件中心仅聚合其入口和状态。
- Android 交互与实施文档由 [Android 文档目录](../../Client/RelaxKonOS.Client.Android/docs/) 拥有。

集中的是产品入口，领域安装器、Helper 验证和原生服务适配器继续由各领域维护。本文不将任何计划中的来源或平台能力标记为已实现。

## 2. 应用、组件与工作负载

三者分别建模：

| 对象 | 示例 | 生命周期 |
| --- | --- | --- |
| 内置应用 | 代理服务端、Web Server、Docker 管理器 | UI 随 RelaxKonOS 发布；宿主组件缺失不删除客户端代码 |
| 宿主组件 | sing-box、Nginx、Docker Engine | 独立版本、安装所有权、来源与运行状态 |
| 工作负载 | 代理服务器基础环境 | 引用组件、功能和可选业务动作；本身不伪装成独立软件包 |

应用与组件是多对多关系。组件分为必需和可选依赖；安装可选组件只解锁对应功能。证书申请、容器镜像更新和业务配置发布不是应用本身的安装更新。没有独立组件的应用不增加虚假的安装状态。

组件描述至少包含 componentId、领域 action/runtime ID、分类、必需/可选依赖、冲突、应用关联、平台约束及展示元数据。描述不能包含任意 shell、可执行路径或安装命令。版本和可执行能力由宿主可信适配器返回，UI manifest 不授予权限。

## 3. 应用显示与打开策略

默认采用“应用可发现，未就绪时引导安装”：有权限且平台支持的应用仍可在应用列表找到，缺失必需组件时标注“需要安装组件”。点击后显示统一对话框：

```text
代理服务端需要 sing-box
当前服务器尚未安装所需组件。
[取消] [前往组件中心]
```

跳转携带 hostId、appId、componentId/工作负载 ID 和受控返回目标；只定位与预选，不自动安装或授权。安装成功后提供“打开代理服务端”，重新检查当前宿主和依赖状态。若应用支持独立的离线编辑功能，可提供明确的受限打开入口，由应用声明能力。

允许用户选择“仅显示已就绪应用”，过滤可启动入口；组件中心仍列出可安装组件。快捷方式、搜索、收藏和深链接即使被过滤也走统一可用性检查，不能报“应用不存在”。组件中心、设置和恢复入口不得因该过滤隐藏。

未安装、停止、故障、未知、外部安装、不支持、无权限分别显示：服务停止不等于未安装；查询失败不得触发安装；待恢复提供恢复入口；平台不支持不给安装按钮；外部安装按领域能力决定仅检测或可管理，不自动接管。权限不足时显示申请管理员处理的原因，不展示无权访问的宿主细节。

状态按 hostId 和实际安装身份缓存并订阅/刷新，切换服务器、断线重连和卸载后重新核对，不能沿用另一服务器的应用可用性。

## 4. 信息架构与页面

组件中心为单窗口系统应用，顶部明确当前目标服务器、平台、架构和连接状态。主要页面为“全部组件”“已安装”“可更新”“工作负载”“任务与恢复”“发布源”。

主体左侧为搜索、分类及可展开的组件/功能树，右侧为详情。树的三态勾选表示功能组的选择聚合；是否已安装、是否运行、版本和故障使用独立状态标记，不能用一个勾选框同时表达。

详情展示：组件用途、关联应用、所有权、当前实测版本、目标版本、来源、平台、安装模式、健康、开机启动、数据位置摘要、依赖、版本支持与验证证据，以及最近操作。更新、修复、回退和卸载使用明确命名的动作，不通过反复勾选猜测意图。

页面底部是“待应用变更”摘要和“预览变更”按钮。选择和取消选择只编辑本地草稿，不执行安装、卸载或信任变更。关闭有草稿的窗口提示保留或放弃；草稿不是已批准计划，重新打开后重新规划。

## 5. 操作流程

| 操作 | 交互与约束 |
| --- | --- |
| 安装 | 选择组件/功能、可信来源、明确版本及必要选项，解析依赖并预览 |
| 更新 | 比较当前与目标版本、配置能力、数据兼容和重启影响；默认仅列当前支持的稳定版本 |
| 修复 | 验证或重新安装同版本，展示会恢复的文件和服务；不能报告为升级 |
| 回退 | 仅列可恢复且当前信任允许的版本，展示配置/数据限制；不保证所有包管理器可回退 |
| 卸载 | 默认保留业务数据，预览程序、服务、自有规则及关联应用影响；删除数据独立确认 |
| 恢复 | 对已有领域事务重试、紧急停止或关账；不以重新安装掩盖结果未知 |

统一流程为“编辑变更 → 解析依赖和来源 → 冻结计划 → 预览 → 审批 → 执行 → 结果/恢复”。执行中的任务可关闭窗口，状态和取消能力由宿主提供。完成页列出成功、no-op、失败、跳过、补偿和保留资源，支持回到关联应用。

更新不默认切换来源或安装模式。切换来源必须显示新发布者、信任和制品身份；不允许的模式转换提示专用流程。批量更新只包含用户明确选择的组件，不自动更新所有发现的新版本。

## 6. 版本与来源选择

“发布源”与“文件从哪里传来”是两个维度，必须分别展示。上传文件、输入 URL 或计算出一个 SHA-256 都不等于可信发布者。

| 输入方式 | 处理规则 |
| --- | --- |
| 已登记网络发布源 | 选择 sourceId、目录中的 releaseId；依赖签名、修订、撤销和平台规则验证，不提交任意下载命令 |
| 服务器文件 | 通过文件选择获得 actor/host 绑定的短期文件引用；宿主在保护暂存区读取并验证，UI 不把任意路径交给 Helper 执行 |
| 本机文件 | 流式上传到目标服务器保护暂存区，限制大小与有效期，返回文件引用；本机路径不被误认为服务器路径 |
| apt 等系统包源 | 使用明确发行版、仓库身份、签名和包集合的领域适配器，冻结精确版本与依赖影响；不运行用户输入的 apt 命令 |
| 镜像/离线介质 | 更换传输位置，仍匹配已受信任的制品身份；镜像不能重定义版本摘要 |

文件导入只能选择该组件支持的包格式，并匹配可信目录或独立签名元数据、平台、长度和完整文件清单。缺少可信依据时阻止安装并说明原因；第一版不提供“仍然运行未知程序”。新增来源和密钥是独立的宿主信任管理操作，先审查并提交，再重新生成安装计划，不能在同一未经确认的导入中静默授信。

网络源新增遵循 SSRF、重定向和凭据隔离规则；普通输入网址不能成为 Helper 信任依据。apt 适配器需声明 package-managed 与外部资源所有权、全局包管理器锁、模拟/解析结果和提交前复核；仓库变化或额外依赖扩大影响时重新计划。禁止全局 purge/autoremove。尚无适配器的平台或组件显示“该来源暂不支持”。

目录刷新失败保留缓存并标明过期，不显示“已是最新版”。版本列表分别显示来源可信度、目标支持、配置能力和验证证据。默认安装版本由可信目录及明确策略选择，规划时冻结 releaseId，执行时不能再解析 latest。

## 7. 依赖与卸载影响

工作负载展开为具体组件和功能。选择父节点可以勾选推荐子项，但必需项、可选项及原因必须可见。共享依赖去重；互斥版本或安装模式不能靠最后一个选择覆盖。

卸载前读取真实依赖、业务配置与运行中消费者，列出受影响应用和服务。默认阻止破坏仍有消费者的必需依赖；若领域支持级联停止/移除，必须将其作为明确步骤单独预览审批。取消某个工作负载不默认删除它曾引用的共享组件。自动带入的新增依赖与用户原有资源分别记录，不因一次后续失败就卸载原有组件。

组件卸载不删除应用入口代码；应用进入依赖未就绪状态。默认保留草稿、业务数据及必要保护密钥，删除数据须遵循领域规范并列出不可恢复项、关联秘密和备份影响。停服、禁用开机启动、卸载程序和删除数据是不同意图。

## 8. 各应用保留的职责

各应用移除独立生命周期管理 UI，只保留共享“组件依赖”区（组件名、宿主实测状态、前往组件中心）与业务能力。依赖区放在应用“设置”页；没有设置页的应用新增一个设置分区，不再使用常驻顶部横幅。业务配置、配置发布、服务启停、业务日志和健康检查继续留在应用。

例如代理服务端管理 inbound、principal、credential 和发布；组件中心管理 sing-box 程序版本。配置回滚仍属于代理领域，程序版本回退属于组件生命周期，预览说明它们的关联。Docker 镜像和 Compose 业务管理也不移入组件中心。

实施时直接替换各应用旧 UI 和调用入口，更新全部调用者、测试与说明，不保留两套规范或旧路由兼容层。领域 API 可以继续作为当前统一服务被组件中心调用；“移除应用安装页”不等于删除成熟领域事务。

## 9. 自身组件维护

Server、Guardian、PrivilegedHelper 单独分组，复用服务器中心既有部署、升级和修复流程。组件中心不能假定能够用正在被替换的 Server Executor 完成自身升级。连接将中断时，交由现有宿主部署通道及外部维护协调者执行，并显示重新连接和验收状态。

保持各安装模式的实际能力：不支持的 Guardian、系统权限或服务宿主不显示为可安装。当前连接故障不能被解释为维护成功，恢复入口应在服务器中心仍可达。

### 桌面首批接入（2026-10-24）

新增内置应用 `relaxkonos.component-center`（单窗口）。当前目录仅开放 sing-box；右侧复用既有可信来源、版本选择、宿主状态、安装/更新/修复/回退/卸载及恢复面板。代理服务端移除运行时页面与卸载按钮，保留业务配置、配置回滚和服务启停，以及组件中心跳转。读取到明确未安装状态时提示前往组件中心；状态读取失败或不支持不按缺失组件处理。

每次版本变更先取得领域冻结计划，再确认服务器、操作、版本、来源及数据保留意图；缺少确认宿主或用户拒绝均不提交安装台账。会话更换会使旧窗口失效。此阶段仍使用领域 RuntimeChangePlan，未实现 TaskPlan 批量编排、全应用依赖目录、来源信任编辑、离线文件导入或 apt 适配；不能据此宣称 CC-01～CC-03 全部完成或 Windows 生命周期已实测。

首批入口接入检查：`dotnet build Client/RelaxKonOS.Client.Desktop/RelaxKonOS.Client.Desktop.csproj --no-restore -m:1`；`dotnet build Tests/Client/RelaxKonOS.Installation.Tests/RelaxKonOS.Installation.Tests.csproj --no-restore -m:1` 后运行 `dotnet run --project Tests/Client/RelaxKonOS.Installation.Tests/RelaxKonOS.Installation.Tests.csproj --no-build --no-restore`，46 项通过。新增检查覆盖冻结计划缺少审批宿主、用户拒绝、确认目标版本，以及删除数据确认与冻结计划确认分别执行。测试使用模拟 HTTP，不替代真实安装、主题与交互验收。

### 桌面草稿与受控导航（2026-10-24）

组件元数据与工作负载分别建模在 `ComponentCatalog`，当前只开放首批 sing-box，不把应用清单当作执行权限。组件中心中的版本动作和卸载动作只暂存 `ComponentChangeDraft`；底部预览入口才重读安装/恢复、来源和目录，再规划、预览并审批。草稿记录精确组件、宿主安装身份、来源、releaseId、变更意图与数据保留选项，不保存冻结计划、提权凭据或审批。实际宿主、安装身份或操作种类发生变化时拒绝旧意图。版本冲突不以最后一次选择覆盖，用户先移除旧变更。

草稿按稳定服务器连接身份和用户 ID 保存在桌面设备本地。关闭时明确选择保留或放弃；关闭确认框本身默认保留。再次打开只恢复意图，重新预览才请求宿主计划；退出桌面进程后的持久化已接入，详见下文。取消工作负载或移除草稿不会触发组件卸载。

### 公共应用启动检查（2026-10-24）

### 通用组件启动门禁与共享依赖区（2026-10-29）

窗口创建前的检查不再绑定 sing-box。`ComponentCatalog.LaunchGate` 由组件目录自身的应用关联生成：同一应用关联的多个组件是**可替代**关系（Tunnel Manager 的 frpc 与 frps 任一满足即可），没有关联组件的应用不获得虚假依赖。观察改用通用 `GET /components/{componentId}/state`，读取权限为该应用声明的 `server.components.read`；分类只依据宿主事实：待恢复 → Recovery、有进行中操作 → Busy、所有权 Unknown/External/Absent → Unknown/External/Missing、其余 → Installed。宿主声明该平台不提供此组件（`component.platform_unsupported`）→ NotRequired，应用照常打开——把平台差异当成“未安装”会凭空阻止应用。

各应用的组件入口统一为共享 `ComponentDependencySettingsView`（组件名、宿主实测状态、前往组件中心、重新检查），放在应用设置页：代理管理器、代理服务端、Docker、SMB、Squid、FRP、Web 服务器新增或复用“设置”页；Project Editor 是编辑器布局，从“工具 → 组件依赖”打开同一个区域。应用内不再有安装、更新、修复、回退、卸载表单或命令，也不再使用常驻顶部横幅；服务启停、配置、站点、隧道、镜像等业务能力保留。设置区与启动门禁共用同一次读取语义，两处不会对“缺失”给出不同结论。

### 按平台声明安装来源与 Nginx 只读观测（2026-10-25）

同一产品的 Linux 与 Windows 实现不同，这是目录必须表达的事实而不是实现细节：

- `ComponentSourceDeclaration` 现在带 `Platforms`。Nginx 在 Linux 是发行版包（`SystemPackage`）加官方源，在 Windows 没有对应包管理器，只能走 RelaxKonOS 受管归档（`ManagedArchive`）加自有服务注册；Squid、Docker Engine、Samba 目前只声明 Linux 来源；frp 与两个代理运行时两端都用受管归档。所有声明仍然 `AdapterAvailable = false`，除两个代理运行时。
- 组件的当前平台来自宿主自己的回答（运行时快照的 `Target.Os`），不是客户端猜测。界面把与当前主机匹配的来源放在「安装来源」一行，其余平台单独折叠为「其他平台」；平台未知时全部归入其他平台，不冒充适用。
- 这条规则同时挡住了「在 Windows 上显示 apt 来源」和「在 Linux 上显示 Windows 归档」两类误导。

**Nginx 的只读主机实测**（本切片不新增任何执行能力）：

- Nginx 不是台账化运行时，它的安装与配置由 Web 服务器管理器以实例方式拥有，且平台分支（Linux 发行版包 + `nginx.service`／Windows 受管归档 + 自有服务）已在 MR-05 的既有代码里。因此组件中心不伪造组件台账，而是新增 `IComponentHostObserver` 抽象与 `WebServerComponentObserver`，通过既有 `IRemoteWebServerClient` 读取实例列表、集成候选与运行状态。
- 面板只显示：平台、管理方式（宿主系统包已接入／RelaxKonOS 受管安装／宿主安装待接入）、已装版本、运行状态与一句说明。显式点「读取主机状态」才发起读取；面板没有任何安装、规划或审批入口，说明文案也写明这一点。
- 目前只有 Nginx 有观测器；Docker、Squid、Samba、frp 仍只有目录项与「打开应用」。给它们加观测器必须复用各自领域已报告的只读事实，不得新开写路径。

**启动就绪门槛收窄为单一事实源**（2026-10-26）：`ComponentCatalog.LaunchGate` 只返回批量接入（当时只有 sing-box）的组件，`ApplicationAvailabilityService` 与 `AppEntryViewModel` 都改用它。此前目录扩容后，Docker／Squid／Web 服务器／内网穿透／文件服务会被误判为「有组件依赖」，从而在启动守卫里显示「无法确认组件状态」并阻止打开——这是一次真实回归，现已修正并由检查覆盖。*2026-10-29：通用状态适配器补齐后门禁重新覆盖全部关联组件，平台不提供按 `NotRequired` 处理，不再触发该回归；见「通用组件启动门禁与共享依赖区」。*

验证：Client Installation **431 项 PASS**（新增「只有带可用性适配器的组件才能拦截启动」「平台实现不同的组件按平台分别声明来源」两条）；WindowPreviews `--component-center-only` 三语言 × 明暗通过，新增「没有宿主平台回答时全部来源归入其他平台」「只显示当前平台可适用的来源」「有观测器的组件提供主机实测面板」「读取事实不宣称组件中心安装」，并保留 HostObservation 渲染图；`--readiness-only` 回归通过。

边界：Nginx 面板显示的是 Web 服务器管理器已有机读事实，不代表组件中心可以安装、更新或卸载它；这些仍属 MR-05 的「统一安装/卸载/更新页面」，尚需按平台分别冻结来源与版本。

### 组件通用计划路由与 Linux 包来源冻结（2026-10-25）

**一条路由，N 个组件。** 此前每个产品各自一组路由（`/managed-runtimes/sing-box/plan`、`/managed-runtimes/mihomo/plan`），计划语义写在服务里，服务端一变就得再写一份。现在新增：

- `GET /api/v1/components/{componentId}/state` → `ComponentStateView`（归一化状态 + 该主机声明的安装方式 + 读不到时的原因）
- `POST /api/v1/components/{componentId}/plan` → `ComponentPlanResult`（冻结目标 + 问题码）

两者沿用运行时的读取/管理授权边界；写操作仍按产品各自权限判定（`InstallationServiceId`），所以共享路由没有扩大任何人的权限。管理权限不足时返回 403，组件未注册时返回 404 `component.unknown`——两者必须可区分，否则拼错组件名会被误读成平台不支持。

**适配器注册表是闭集。** `IComponentLifecycleAdapter` 只做一件事：把某个产品的领域事实翻译成 `ComponentState`/`ComponentPlanResult`。注册表在组合期校验（未知名或同组件重复注册直接失败），运行期只认注册过的组件。本切片只注册两个：

| 组件 | 安装方式 | 适配器 | 能否执行 |
|---|---|---|---|
| sing-box | 受管归档 | 委托既有 `SingBoxRuntimeService`（同一冻结计划、同一台账） | 是（不变） |
| nginx | Linux 系统包 | 读宿主包管理器解算结果 | **否**：冻结可用，安装事务未实现 |

nginx 在 Windows 声明的仍是受管归档，本构建没有对应适配器，因此显式返回 `component.execution_unavailable` 而不是退回 Linux 的 apt 路径。

**Linux 包来源冻结做了什么。** 特权助手新增只读操作 `NginxPackageQuery`：

1. `apt-cache policy nginx` 给出版本与**每个版本由哪个仓库发布**（基址 + suite/area + 架构）；
2. `apt-get install --print-uris nginx=<候选版本>` 给出该事务将要下载的确切工件：pool 地址、字节数、SHA-256，以及同事务的依赖包；
3. 两者合成为一条 `ComponentPackageTarget`：包名、版本、架构、`仓库身份`（`baseUri|suite|area|arch`）、pool 地址、摘要、依赖集。

没有任何 `apt-get update`、下载或安装；它就是「宿主自己的解算结果」。拒绝的边界也写死：没有发布仓库的本地 `dpkg` 记录不能当来源、摘要必须 64 位十六进制、超过 512 MiB 或零字节的工件直接拒绝、非 HTTP(S) 位置不算仓库工件、`file:` 假工件不算冻结。

**为什么冻结了却不可执行。** 一个能冻结却不能安装的计划，如果 `Allowed=true`，就会在界面里读成「可以装」。所以 `NginxPackagePlan.Evaluate` 在返回冻结目标的同时固定附加 `component.execution_unavailable`，`Allowed` 恒为 false；界面把这一行渲染成「冻结完成但不可执行：本版本尚未接入该来源的安装事务」。包没有台账，因此 `State.Revision` 用「已装版本 + 候选版本 + 摘要 + 归属」的哈希派生：事实一变修订就变，过期计划会撞 `component.state_revision_conflict`，而不是悄悄按新事实执行。

**桌面。** nginx 页新增「安装来源冻结」面板：安装方式（本机声明的模式 + 平台 + 可解算/未接入）、已装版本、候选版本、发布仓库、同时安装、SHA-256、以及那句拒绝原因。必须显式点「解算安装候选」，面板里没有任何安装/审批入口。

验证：`RelaxKonOS.Server.Tests --components-only` **44 项 PASS**（路由与授权边界、注册表闭集语义、修订派生、apt 策略/工件/合成与五类拒绝、状态映射、计划判定、适配器平台分支、客户端契约往返）；Client Installation **446 项 PASS**（新增 15 项 `ComponentLifecycleClient`：路由、令牌、请求原样传输、冻结结果与拒绝、403/401/404/409/503 映射且不泄漏宿主诊断、畸形与超大响应、会话变更）；WindowPreviews `--component-center-only` 三语言 × 明暗通过并输出 PackageFreeze 渲染图；`--readiness-only`、`--desktop-actions-only`、桌面客户端编译通过。

边界：本切片只做到「按组件通用的计划路由 + 一个真实的系统包来源冻结」。**没有**实现 Debian 包安装事务（依赖解析后的落盘校验、失败回滚、`nginx.service` 生命周期归谁），也**没有**实现 nginx 的 Windows 受管归档分支。TaskPlan 批量层（审批/执行/对账）仍只对 sing-box 生成动作，nginx 尚不能进入任务台账。

已知遗留：`RelaxKonOS.Server.Tests` 在当前 HEAD 无法编译——`NetworkProxyTunnelChecks.cs` 仍调用 MR-03 台账切换时已删除的 `MihomoRuntimeManager.InstallManagedAsync`（7 处）。该断点与本切片无关，`--components-only` 因此通过临时工程引用同一份检查源码运行；修复方式是把这些过时的固定清单安装检查删除或改写为台账路径。

## 简约主界面与任务弹窗（2026-10-26）

日常页面只提供全部组件、已安装、可更新及来源浏览；组件列表仅用于定位，不显示批量勾选。详情默认展示组件名称、状态、版本和安装操作，接入方式、发布来源、摘要、宿主诊断与完整日志折叠。组件身份放在操作之前；移除重复的安装进度与取消按钮。

批量任务是预定义场景/已支持组件操作的专用计划流程，不是通用脚本执行器。其场景选择、组件勾选、草稿、只读预检、冻结计划、审批、历史、结果、进度及人工恢复均由独立“组件任务”模态弹窗承载。主界面不因注入任务服务而常驻“受管任务”，也不显示草稿底栏或批量任务导航。主界面保留“任务…”入口，生成新的批量草稿自动打开该弹窗；任务/工作负载导航链接定位组件后打开弹窗，普通组件浏览上下文保持可用。

弹窗内的审批、凭据和恢复确认必须以当前任务弹窗为父级；保留原有宿主、登录、权限、修订和显式确认门禁。关闭弹窗只收起界面，不丢弃草稿、不取消已受理任务；原后台轮询继续，由用户显式取消或恢复。没有历史任务时仅提示空状态和刷新记录，不展示空进度、结果及恢复控件。任务弹窗关闭按钮与 Escape/标题栏关闭均在显式请求或预检尚未完成时遵循取消门禁。此次调整不改变任务契约、执行器、安装所有权或信任边界，也不增加脚本执行能力。

## 服务端模块分区

组件中心包含独立的“服务端模块”分区，与宿主软件目录、授权和安装台账分离。桌面已接入模块事实、驻留详情和配置启停计划；移动端支持边界由 Android 自有文档拥有。完整入口、当前实现限制、部署配置和 MM 跟踪见[服务端模块管理设计 §12](../architecture/RelaxKonOS.ServerModuleManagement.Design.md#12-当前实现边界与部署配置)。既有宿主组件状态和 CC/MR 验收不因模块分区而改变。
