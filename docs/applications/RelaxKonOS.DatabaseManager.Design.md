# 数据库引擎管理设计（APP-005）

> 状态：DB-01 已核实，DB-02/03/04、DB-05 指定来源 TLS 与 DB-06 补丁维护切片已实现并通过隔离 systemd/PostgreSQL 验收。DB-07D 扩充原生平台矩阵，验收范围见下文。更新：2026-11-17。
> 本文拥有数据库领域设计与 DB 跟踪项；[原提案](../application-ideas/proposals/DatabaseManagement.md)保留需求入口。本文的实施顺序是建议，不能作为支持矩阵或交付承诺。

## 1. 决策摘要

先做 **PostgreSQL 单实例的安装、建库建账号、改密、连接与服务维护闭环**，再以 MySQL 验证公共模型是否真正支持第二种引擎。不要同时启动多个引擎、所有平台和两套安装模式。

建议首个验收目标为 Ubuntu 24.04 LTS x64、直接安装、发行版已配置且签名有效的软件仓库中的 PostgreSQL 16 系列。该组合已完成 [DB-01 版本与来源核实](RelaxKonOS.DatabaseManager.PostgreSql.DB01.md)，不表示产品已支持；实施时必须冻结准确包版本、依赖及来源，不能仅冻结“16”或“最新版”。选择这个组合是为了控制第一轮适配范围，不代表它是最新版本。若仓库或目标机不满足条件，应先修订矩阵，不能静默加源或改用容器。

首轮开发只承诺本机连接；形成可交付 MVP 前补齐指定来源的 TLS 访问、同主版本真实跨补丁更新、保留数据卸载和中断恢复。管理员凭据完全遗失后的恢复另设验收门禁。随后接入 Windows x64 直接安装和 MySQL LTS；Linux Docker 依赖公共容器组件机制补齐后接入。

既定产品方向保持：Windows 直接安装；Linux 可选直接安装或 Docker。安装模式取决于目标 Server，不能由客户端操作系统决定。详情复用[直接安装与 Docker 统一设计](../application-ideas/NativeAndDocker.md)。

## 2. 流行程度与引擎顺序

依据 [Stack Overflow 2026 数据库调查](https://survey.stackoverflow.co/2026/technology/data/databases)，该题全体回答者为 12,061 人。下列为过去一年使用比例，多选结果不能相加，也不是生产装机量、市场份额或 RelaxKonOS 用户需求统计。核对日期为 2026-11-16。

| 引擎 | 调查使用率 | 本产品建议 | 取舍 |
| --- | --- | --- | --- |
| PostgreSQL | 57.9% | 第一实现 | 通用关系库，先建立完整实例管理路径 |
| SQLite | 42.1% | 独立文件工具方向 | 无独立数据库服务，不套用服务、端口与管理员恢复模型 |
| MySQL | 35.1% | 第二实现 | 补齐常见 Web 应用依赖；独立处理用户与来源主机身份 |
| Redis | 28.3% | 第二阶段候选 | 缓存、会话和队列；ACL、持久化和关系库不同 |
| SQL Server | 27.1% | 明确业务需求后 | 安装、版本类别、资源与许可评估成本更高 |
| MariaDB | 20.3% | 第二阶段候选 | 指定依赖优先；不作为 MySQL 的可替换版本 |
| MongoDB | 19.0% | 后续 | 文档型需求明确后再适配认证数据库及拓扑 |
| Valkey | 5.0% | 与 Redis 一起评估 | 分开核实兼容性、发行源、许可及真实应用需求 |

上述顺序是基于调查与实现成本的产品判断，不是按百分比机械排序。第一阶段 PostgreSQL → MySQL；第二阶段有 MariaDB 指定依赖时优先 MariaDB，否则先选择 Redis/Valkey 中与目标应用相符的一种。ClickHouse、Oracle、分布式数据库与云数据库控制平面暂不纳入。

版本选择采用受支持稳定系列，不追逐最新大版本。PostgreSQL 官方区分主版本迁移和次版本更新，主版本通常支持五年，见[版本政策](https://www.postgresql.org/support/versioning/)。MySQL 第二实现优先评估 8.4 LTS，并在立项时复核支持期、平台和应用兼容性；不默认同时覆盖 Innovation，见[官方发布模型](https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html)。

## 4. 用户流程与信息结构

应用首页按实例展示引擎、实测版本、运行状态、所有权、访问范围、健康与最近操作。没有实例时提供“选择引擎”，预填上下文跳转组件中心，不复制安装页面。

1. 组件中心选择明确版本与模式，预检空间、端口、路径、服务、来源和依赖，展示完整影响后执行安装计划。
2. 返回数据库应用初始化实例：指定名称、专属数据目录、端口和开机启动；程序安装成功与实例就绪分别显示。
3. 创建逻辑数据库和专属应用账号，展示授权范围，使用新身份验证连接与授权。
4. 展示主机、端口、数据库、用户名、TLS 要求及外部客户端连接说明；密码默认隐藏，连接信息默认脱敏。
5. 需要异机连接时创建指定来源访问计划；分别显示监听、认证、TLS、防火墙和验证结果。

详情分为“概览、数据库与账号、连接与访问、维护与操作记录”。维护显示启停、重启、日志和组件中心跳转。失败信息包含可处理原因、原操作 ID 和恢复入口；客户端关闭后可找回原任务。Android 专属交互与布局后续只在 [Android 文档目录](../../Client/RelaxKonOS.Client.Android/docs/)维护。

## 5. 领域模型与职责

| 对象 | 必需语义 |
| --- | --- |
| EngineCapability | engineId、平台/版本/模式范围、动作支持与阻止原因、验收证据引用 |
| RuntimeInstallation | 引用组件中心 installationId、releaseId、来源与程序修订，不复制安装台账 |
| DatabaseInstance | 稳定 instanceId、hostId、engineId、安装引用、native/docker、所有权、数据与配置身份、修订 |
| RuntimeBinding | 原生服务身份或容器/部署身份；更新可替换，不能充当 instanceId |
| Database / Principal / Grant | 引擎原生名称与身份、实例归属、权限模板和实测授权；MySQL 用户身份包含 host |
| CredentialReference | 受保护秘密引用、用途、修订及依赖应用；普通状态不返回秘密 |
| AccessPolicy | 地址族、监听、允许来源、认证、TLS 引用、规则所有权、配置与验证修订 |
| OperationEvidence | 原操作 ID、冻结修订、阶段、实际版本/身份/连接验证、补偿结果和未解决责任 |

客户端通过共享当前协议表达意图；Server 数据库领域负责权限、实例目录、计划、串行协调和结果投影。引擎适配器负责原生认证、授权、配置及数据格式语义；运行后端负责 native/docker 差异。不能用一个拼接 shell 的万能适配器代替二者。

组件中心拥有软件生命周期；Helper 复核特权动作、信任、受管路径及服务归属；Docker 领域唯一执行容器操作；防火墙、证书与秘密复用已有权威。数据库领域持有资源引用与业务期望，不能另建防火墙写入器或 Docker CLI。数据库进程由系统服务或容器宿主独立运行，不作为管理模块子进程。

模块只在有管理工作时持有工作租约，已受理操作的收尾和恢复必须有持久责任。存在未交接恢复责任时拒绝停用模块；正常停用、休眠或卸载管理应用不能顺带停止数据库。不得让 Core 为数据库管理而长期加载全部驱动。

## 6. 计划、操作与权限契约

以下是待实施的语义设计，不宣称已有路由。实例读取、实例创建、服务动作、建库、创建账号、授权、轮换凭据、访问配置及恢复采用类型化请求；没有任意 SQL、shell、安装参数或任意文件写入入口。实现时共享协议、调用者、测试与文档一次更新，不保留旧接口兼容层。

写入先形成计划，包含 hostId、instanceId（新建时预分配）、安装/配置/凭据预期修订、动作、停机与依赖影响、到期时间和明确验证步骤；安装计划复用组件中心并冻结来源、信任与制品。提交携带 planId 与幂等键，执行前重新核对授权、所有权及修订。相同键返回原操作，内容不符拒绝；过期或漂移要求重新计划。

状态区分 Planned、Running、Verifying、Succeeded、Failed、NeedsRecovery、Cancelled。未收到应答不等于失败或成功；按原操作 ID 查询并核对副作用，不能自动重发改密、建库或删除。只在安全阶段接受取消。成功须绑定当前资源身份及实际验证证据。

实例写入与安装维护共用协调锁；共享安装还要锁定受影响实例集合。多领域操作采用固定锁顺序并保留子操作回执，不声称跨数据库、秘密库、防火墙具有原子事务。审计记录操作者、作用域、目标与阶段，不记录密码、完整连接串和原生命令输出中的秘密。

权限分开为只读、实例控制、账号与授权管理、网络配置、宿主安装、管理身份恢复及数据删除。查看实例不授予读秘密权限；主机登录权限不自动获得数据库管理权限。

## 7. PostgreSQL 首个适配

### 7.1 安装、初始化与健康

APT 安装冻结包及依赖，预检包脚本是否自动创建/启动默认集群，不能假设安装仅写程序文件。已有集群、服务、端口或目录发生冲突即停止计划，不接管或覆盖。初始化使用专属低权限服务身份与空的受管数据目录；明确数据目录、配置文件、服务和端口的归属。

服务状态、实际加载版本、数据目录身份、认证连接分别验证。健康探针使用受限身份执行固定只读查询；端口可连、进程存在或 readiness 探针成功不足以证明业务认证成功。写入持久化和授权隔离在验收数据库中验证，不在日常健康检查中创建业务数据。

### 7.2 数据库与账号

初始模板区分数据库所有者/迁移角色和日常读写角色，默认应用身份无超级用户、创建角色或创建数据库能力。授权需覆盖 database、schema、既有对象及未来对象；检查 PUBLIC 默认权限，不能只授予 CONNECT 就声称实现数据库隔离。只读与读写模板通过真实正反向 SQL 测试确认。

用户名、数据库名等标识符采用严格校验与引擎专用引用规则，秘密通过安全驱动或受保护通道传递。禁止将密码拼到命令行或普通日志。管理身份采用受保护凭据或已确认的本地身份认证；peer/socket 不应被误判成“没有密码导致故障”。

### 7.3 密码修改与恢复

正常改密：确认目标和依赖 → 生成待用秘密引用 → 执行原生修改 → 用新凭据新建连接验证 → 核对旧凭据的新连接行为 → 提交引用并提示依赖应用更新。连接池中的既有会话是否持续单独说明。

应用凭据与数据库修改无法原子提交时，明确“数据库已改密、应用待更新”；不能恢复已撤销密码或报告全部成功。应答中断时先使用受保护待用凭据只读验证，不重新随机生成密码。

管理凭据仍有效时重置应用密码属于普通账号管理。管理凭据完全遗失的恢复需要独立授权、已证明所有权、目标版本/模式专属流程及维护窗口。恢复期间阻断外部连接，持久记录临时认证和原配置；只有恢复正常认证并验证成功才结束隔离。失败或宿主重启后保持隔离与 NeedsRecovery。DB-04 通过前不开放此能力，不以普通改密冒充已实现。

### 7.4 连接范围

默认只监听回环。首个外部访问能力仅允许明确 IP/CIDR 或 VPN 来源，不提供“一键全部公网”。非回环访问必须配置并验证 TLS 与密码认证；不能因私网而省略认证。

监听地址、`pg_hba.conf` 首条匹配规则、角色权限与防火墙分别规划。生成 SCRAM 认证规则并核对规则顺序、IPv4/IPv6、原生解析错误及实际生效配置。PostgreSQL 的 HBA 在 Linux 与 Windows 上生效行为不同，按平台处理，见[官方 HBA 文档](https://www.postgresql.org/docs/current/auth-pg-hba-conf.html)。

开放采用先收紧防火墙、配置并验证认证/TLS、最后开放允许来源的顺序；各步失败撤销本次自有资源。关闭先阻断新外部访问，再收窄监听和认证。保留管理通道，既有会话需要断开时单列影响与操作。

状态分别显示“已配置”“本机已验证”“指定外部来源已验证”，记录来源、目标、时间与配置修订。云安全组和 NAT 不在管理范围时明确列出；本机成功不能标记外部可达。

## 8. 更新、数据与其他引擎

遵循[受管运行时设计](../platform/RelaxKonOS.ManagedRuntimes.Design.md)、[包所有权](../platform/RelaxKonOS.PackageOwnership.Design.md)及[组件中心](../platform/RelaxKonOS.ComponentCenter.Design.md)。程序、数据、配置、备份和保护密钥分离；归档版本目录不可变，APT 走包事务，不冒充归档切换。针对既有 Windows 其他组件的文件安装特例，不自动扩展为数据库信任策略。

同版本重装只称修复，不能覆盖数据。首版更新仅开放经过验收的同主版本路径，要求至少两个不同真实版本；计划核实升级说明、依赖、空间、停机、备份与恢复条件。上游新版本被发现不等于可安装；无法获得可信旧版做更新验收时，DB-06 保持未完成。

备份必须使用引擎一致性方案或验证过的停机副本，包含角色/授权、配置与必要密钥引用；成功生成文件不等于可恢复。MVP 的更新门禁需在隔离目标验证恢复、代表性数据与权限，备份自动调度和完整 UI 可后续接入 [APP-001](RelaxKonOS.BackupRecovery.Contract.md)。

DB-07B 已追加经过隔离验收的 Ubuntu 24.04 amd64 受管 PostgreSQL 16.15→18.7 显式复制迁移，范围和恢复边界见[主版本迁移](RelaxKonOS.DatabaseManager.PostgreSql.DB07B.md)；数据格式降级与自动回退不提供。失败后只有确认旧二进制能读取数据、原身份与配置有效且授权未撤销时才能补偿启动；否则保持停机待恢复，不能把二进制指针切回当成数据库回滚成功。

卸载默认保留数据和必需密钥，保留记录用于后续重装核对。删除数据是独立明确计划，枚举目录、卷、备份与引用影响；不能全局 purge/autoremove、删除共享程序或外部资源。共享引用未解除时拒绝移除。

MySQL 适配必须单独实现 `(user, host)` 身份、认证插件、授权、TLS、初始化与管理员恢复；MariaDB 不复用 MySQL 版本策略。Redis/Valkey 分别建引擎身份，采用 ACL 与持久化语义，不套关系库建库/授权。Docker 初始化秘密只对首次空卷有效，修改环境变量不能冒充已有实例改密；镜像 digest 固定，卷保留及恢复受数据库数据格式门禁约束。

## 10. 验收与退出条件

| 场景 | 必须证明 |
| --- | --- |
| 新安装 | 冻结制品与实测版本一致，服务/目录/监听属于实例，认证成功，重启后数据保留 |
| 账号隔离 | 应用能做授权读写，不能访问其他实例/库的受限数据、提升角色或取得管理秘密 |
| 改密 | 新连接成功、旧凭据行为符合策略、既有会话如实呈现；应用更新失败不伪报成功 |
| 外部访问 | 从允许和禁止来源分别测试，证书身份匹配，IPv4/IPv6 不绕过策略；关闭后的会话行为明确 |
| 冲突与外部资源 | 端口冲突、非空目录、未知服务、签名失败、权限不足均不覆盖既有资源 |
| 更新与修复 | A→B 真实不同版本、数据与权限保持；同版修复不算升级；恢复副本可读且权限正确 |
| 中断与补偿 | 安装/改密/网络变更的应答丢失、Server/Helper 重启后沿原 ID 对账；未知副作用不重放 |
| 管理恢复 | 隔离期间无外部免认证窗口；各阶段中断后仍隔离；恢复正常认证才开放 |
| 生命周期独立 | 管理模块停用后数据库继续服务；升级测试中 Core 与无关模块保持可用 |
| 数据删除 | 默认卸载保留数据与密钥；显式删除只影响已证明属于目标的资源 |

每条证据记录 OS/架构、引擎与精确版本、模式/来源、操作 ID、步骤、预期与实测、时间和遗留问题。模拟测试只验证契约及状态机，不能替代真实引擎验收。服务端模块变更按仓库要求优先只更新签名模块包；必须部署完整 Server/Helper 时记录原因。

## DB-07D PostgreSQL 原生平台扩展

Helper 从宿主 `os-release`、进程架构和 systemd 判定准入。按平台选择发行版自带的 PostgreSQL 主版本，保留原 Ubuntu 24.04 组合。Debian `stable` 系列源须由已有 APT 索引确认实际为 `trixie` 系列，再使用固定代号刷新私有索引。Debian 归档与安全更新分别使用 Trixie 归档和安全密钥。Ubuntu 继续核对指定归档指纹。系统 APT 配置保留原样。
