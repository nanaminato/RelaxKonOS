# 注册表编辑器重设计方案

状态：设计草案。范围：RelaxKonOS 的配置注册表与桌面注册表应用，Windows / Linux 使用相同模型。本方案参考 Windows Regedit 的身份结构和交互，不提供对宿主 Windows Registry、任意数据库或机密的通用编辑。

实施进度（以仓库实现为准）：第 9 节的第 1、2、3 阶段已落地——显式上下文与完整地址、HKCU/HKU 同源映射与当前用户标记、按需加载与地址栏导航、能力一致的菜单、状态栏与加载/无值/失败/拒绝访问/断线的分别呈现、schema 元数据与按类型编辑、恢复默认、revision 冲突与固定目标回调、自定义值重命名。第 1 节列举的问题据此均已按方案处理（HKEY_USERS 的账户发现仍按需枚举：折叠后重新展开会重新拉取）。第 4 阶段（受限查找、导出/导入）尚未实施。实现与本文描述不一致时以实现为准。

## 1. 已确认的问题

当前 `RegistryEndpoints.Users` 返回 `users.List()` 的全部账户，客户端将每个账户都放进“其他用户”，没有过滤当前 JWT 用户。因此，当前登录 nanami 时，“当前用户”和“其他用户 → nanami”确实可以解析为同一 UserId 和同一 Workspace。截图不能据此证明跨用户数据混淆；已确认的是账户发现与树的命名不一致。

当前用户请求省略 targetUserId，另一个入口显式指定 UserId；服务器最终都通过用户仓储解析同一 Workspace。现有 scoped client 已固定目标用户，但键/值响应缺少可供界面校验的完整所有者信息。

其他问题：

- 当前用户嵌套在 HKEY_USERS 下，缺少独立的 HKEY_CURRENT_USER 入口；“其他用户”实际表示全部用户。
- 当前登录用户名、服务器、目标用户名和作用域没有同时展示，无法直观看出修改影响谁。
- 托管 JSON 同时作为 `(Default)` 和字段显示，对象也同时出现在值表和子键树，重复暴露存储细节。
- 编辑对话框允许任意改变托管字段的名称和类型，最后才由服务器拒绝；Boolean、枚举、颜色等仍要求编辑 JSON 文本。
- 管理键的创建/删除菜单只按 Workspace 判断，与服务端受托管结构保护规则不一致。
- 空值、加载、失败和权限不足的展示不充分；刷新用户列表、旧请求错误覆盖新选择等状态仍需统一处理。
- 修改回调主要按 scope/path 判定归属，不能仅凭这两个字段区分不同用户的同名键；编辑器应携带不可变的完整目标地址。

Windows 的 HKEY_CURRENT_USER 是当前用户配置的便捷入口，映射到 HKEY_USERS 中的当前用户分支。这种同源关系是正常的，但需要明确表达。[Microsoft：Predefined Keys](https://learn.microsoft.com/en-us/windows/win32/sysinfo/predefined-keys)

## 2. 身份与树结构

推荐移除“Current User / Other Users”人为分组，提供两个并列入口：

```text
注册表 — 192.168.1.5
├─ HKEY_CURRENT_USER — nanami
│  └─ Workspace
│     ├─ Browser
│     ├─ Desktop
│     │  ├─ desktopDisplay
│     │  └─ desktopExperience
│     ├─ Explorer
│     ├─ Terminal
│     ├─ WindowManager
│     └─ Custom                 # 仅存在或用户新建后显示
└─ HKEY_USERS
   ├─ nanami [当前用户]
   │  └─ Workspace              # 与 HKCU 同源，未复制数据
   └─ alice
      └─ Workspace
```

HKEY_USERS 表示全部已注册的 RelaxKonOS 用户，有权限的用户可发现其配置单元。当前用户在其中明确标注“当前用户”；不再使用“其他用户”名称。若产品最终选择只显示其他账户，则必须命名为“其他用户”并过滤当前 UserId，不能与 HKEY_USERS 的全部用户语义混用。本方案选择前一种结构。

账户的判断依据是登录用户的稳定 UserId，不是用户名、宿主 SID/UID、服务运行账户或提权账户。用户名用于展示；同名账户通过短 UserId 区分，属性面板提供完整 ID。Windows SID 与 Linux UID 不能充当跨平台注册表的统一地址。

HKEY_CURRENT_USER 只是当前 JWT 用户配置单元的语义入口。两入口的读取、写入、事件订阅和客户端缓存必须规范化到同一地址，因此修改后立即保持一致。这里的同源入口不是旧 API 的兼容别名。

界面只展示确实支持的作用域。当前主要是 Workspace；User / Device 在有真实数据且权限和契约支持时展示，不添加空分支充数。跨用户 Device 仍不支持。没有机器级配置提供者时不展示 HKEY_LOCAL_MACHINE；不添加假的 HKEY_CLASSES_ROOT、HKEY_CURRENT_CONFIG 或 .DEFAULT。

## 3. 所有者与地址契约

新增由服务端提供的注册表上下文，至少返回：ServerId、当前 UserId / 用户名、WorkspaceId、可浏览范围和当前能力。身份信息从认证上下文和服务端仓储解析。

统一地址模型：

```text
RegistryAddress = (ServerId, OwnerUserId, Scope, ScopeId, KeyPath)
RegistryValueAddress = (RegistryAddress, ValueName)
```

ScopeId 由服务端根据所有者和受支持的作用域解析；不能通过客户端传入任意 WorkspaceId 获得访问。API 请求携带明确的所有者及 Scope，响应回显实际所有者、ScopeId 和键地址，客户端核对后再应用结果。

推荐当前接口直接升级为：

- `GET /registry/context`：当前会话上下文。
- `GET /registry/users`：授权范围内的账户发现，返回稳定 ID、显示名、isCurrentUser、是否存在可浏览 Workspace。
- `/registry/users/{userId}/keys`：列举、创建、删除键。
- `/registry/users/{userId}/values`：列举、读取、修改、删除值。

键路径和 Scope 使用结构化参数；用户名、翻译后的树节点文字与地址栏文本不参与授权。响应带同一完整地址。地址栏接受 HKCU / HKU 缩写用于输入，立即规范化为完整名称；不保留旧的 `HKEY_USERS\Current User`、`HKEY_USERS\Other Users` 解析、旧可选 targetUserId 路由或其他兼容适配。

示例：

```text
HKEY_CURRENT_USER\Workspace\Explorer
HKEY_USERS\<UserId>\Workspace\Explorer
```

在 Alice 的配置单元浏览时，地址栏使用 Alice 的稳定 ID，旁边显示“目标：alice”；不会把本机 Windows 登录用户 betha 当作远端 HKCU。

## 4. 权限与提权

| 操作 | 当前用户 | 其他用户 |
|---|---|---|
| 读取支持的配置 | 正常账户权限 | 目标用户的精确授权 |
| 修改可编辑设置 | 正常账户权限 | 目标用户的精确授权 |
| 新建/删除自定义键值 | schema 与作用域允许 | 同时要求目标用户授权 |
| 修改托管字段名称/类型、删除托管结构 | 不允许 | 管理员也不允许绕过结构规则 |
| 用户列表发现 | 返回自己或已允许的账户 | 受保护的枚举授权 |

管理员资格按当前宿主策略在每次操作时重算，自动授权；普通用户继续使用现有管理员认证。手工授权仍与 JWT jti、原操作者、能力、目标用户和有效期绑定。枚举授权不授予全部用户的数据访问或写入；目标用户授权不扩展到其他用户。

提权提供管理员权限，不切换当前用户：即使认证时输入 Administrator/root，HKCU 仍指向原登录用户。对 Alice 的编辑对话框必须在提权前固定 Alice 的完整地址，重试时保持该地址。

界面用锁图标和“需要管理员权限”表达权限状态；管理员无需额外确认。不得用保留管理员密码、通配目标授权或前端隐藏按钮代替服务端授权。每一次创建、修改、删除、导入和恢复默认都在服务端重新验证。

审计记录操作者、目标用户、完整键和值地址、动作、授权来源和变更版本；不记录密码、令牌或机密原值。

## 5. 值模型与编辑器

托管设置继续只保存在一个权威配置文档中；字段/子对象是其受控视图。日常值表不显示作为内部文档载体的 `(Default)` JSON，也不同时把一个对象重复显示成值和子键。

- 标量字段显示为值行；对象显示为子键；数组使用明确的列表类型或结构化编辑。
- 自定义键的真正无名值显示为“(默认)”，与内部文档载体区别开。
- schema 提供 ValueId、显示名、逻辑类型、可读/可写/可删除/可重命名能力、默认值、约束、枚举候选、说明与生效方式。
- 托管字段的名称和类型只读；自定义值按允许能力新建或重命名。

| 类型 | 编辑方式 |
|---|---|
| Boolean | 开关 / 是与否选择，不要求输入 `true` JSON |
| 枚举 | 本地化候选列表，显示友好名称，保存稳定值 |
| String / Path | 单行编辑、长度限制、路径规则；字符串不要求手工加引号 |
| Integer | 数字框，可切换十进制/十六进制显示，服务器始终接收数值 |
| Number | 有范围与精度的数值框，如终端字号 |
| Color | 色板、预览与合法色值输入 |
| 字符串列表 | 可增删的列表 / 多行文本 |
| Json | 仅真正的复杂或自定义 JSON 使用原始编辑器，带语法错误定位 |

继续显示真实的 RelaxKonOS 逻辑类型，不把 Boolean/JSON 冒充 REG_DWORD/REG_BINARY。借鉴 Windows Regedit 的名称、类型、数据列与双击编辑行为，不声称实现宿主注册表格式。

恢复默认是一种 schema 校验后的显式写入；不删除托管字段，也不改变无关字段。生效说明使用“立即生效 / 重新打开应用后生效”，不在普通流程展示后台持久化和同步队列细节。

## 6. 布局与交互

窗口保留轻量的菜单、地址栏、左右分栏和值表。顶层服务器节点显示连接目标，避免同时连接两台机器时混淆。

- 地址栏支持粘贴完整路径、回车跳转、Ctrl+L、路径历史、Alt+左/右；查找返回完整所有者地址。
- 键树按需加载、折叠保留已有节点、刷新当前分支，不扫描所有用户和所有键；待加载节点提供真实的可展开状态。
- 值表采用“名称 / 类型 / 数据”，可排序、调整列宽，长数据省略并可复制；没有值的父键仍能看到子键导航。
- 单击选择、双击编辑；Enter 编辑值，F5 刷新分支，Ctrl+F 查找，F3 下一个，右键菜单与顶部菜单使用同一能力模型。
- Delete 仅在允许删除时启用；托管键提供“恢复默认”，不提供会被服务端拒绝的删除、新建字段和改类型菜单。
- F2 仅用于可重命名的自定义项；托管字段名称不可改。
- 状态栏显示目标用户名、作用域、值数量和必要权限状态。加载、无值、读取失败、拒绝访问和断线分别呈现，失败不伪装为空。
- 中/英/日只本地化标签和说明，不翻译协议路径、值 ID 或类型稳定标识；跟随现有主题与标题栏样式。

选择其他用户的字段时，编辑对话框顶部显示“服务器 → 用户 → Workspace → 完整键路径”，保存按钮旁提供简短影响说明。弹窗目标不可随后台选择或树刷新改变。

## 7. 并发、一致性与缓存

所有缓存与订阅键包含 ServerId、OwnerUserId、Scope、ScopeId 和 KeyPath。HKCU 与 HKU 当前用户入口共享同一规范化缓存；不同用户的同名路径绝不共享。

导航、树展开、查找、属性和写入分别使用请求代次与取消标记。响应回显的地址必须与请求地址相同；迟到响应和错误不能覆盖新选择的列表、状态或权限提示。取消不代表写入未发生，失去写入结果时先读取核实，不自动重复写。

写入固定目标地址及文档 revision，通过 CAS 修改唯一权威文档。由于同一托管文档的多个字段共享 revision，冲突时重新读取文档并只展示本次编辑字段的差异；不得静默覆盖其他字段，也不无限重试。

成功修改后按完整文档地址失效 HKCU/HKU 两入口的相关分支，更新两个入口的值与能力；刷新保留展开状态、滚动位置和可定位的选择。保存回调必须比较所有者，而不只是 scope/path。

## 8. 查找、导出与导入

查找默认限定当前用户的当前分支，显示搜索范围，可选名称/数据；跨用户搜索只在已授权的目标用户内进行，不能借查找绕过提权。结果带完整地址，取消与迟到响应同样隔离。

导出使用 RelaxKonOS 自有的版本化 JSON 格式，包含逻辑路径、类型和值，不输出凭据或内部文档载体；不生成会被 Windows regedit 当作宿主注册表执行的 `.reg` 文件。

导入先预览目标用户、增加/修改/恢复默认操作及风险，逐项验证 schema 和权限。跨用户导入需要显式选择目标与精确授权；文件中的 owner ID 不能直接决定写入对象。提交提供每项结果，不宣称跨文档事务；失败后不自动重放已成功的项目。

查找、导入和导出在身份、地址、能力与并发基础完成后实施，不作为首轮阻塞条件。

## 9. 实施顺序

1. 身份与协议：显式上下文及完整地址，HKCU/HKU 同源映射，当前用户标记，权限和审计测试。移除旧分组与旧路由，不添加兼容层。
2. 基础交互：稳定的异步状态、按需加载、地址栏导航、能力一致的菜单、别名入口联动。
3. 设置编辑：schema 元数据、按类型编辑、恢复默认、文档版本冲突与固定目标回调。
4. 扩展管理：受限查找、差异预览、导出/导入。

这一顺序先消除“修改谁”的歧义，再提升编辑效率。第一轮不新增机器级或宿主注册表范围，不复制已有应用设置的数据来源。

## 10. 验收标准

- 当前用户是 nanami：HKCU 显示 nanami；HKU/nanami 明确标记当前用户。两个入口读取同一版本，任一入口修改后另一入口更新。
- nanami 与 alice 都有 `Workspace\Explorer`：修改 Alice 不改变 Nanami，所有返回值和回调携带各自完整地址。
- 本机 Windows 用户 betha 连接远端 nanami：HKCU 仍表示远端 nanami；用另一管理员提权后该身份不改变。
- 普通用户未提权不能读取/修改别人的数据；管理员无额外弹窗；一个用户的授权不能用于另一个用户；失效、撤权与会话切换立即重新检查。
- 同名显示账户、无 Workspace、未知或已删除用户、无 Device 权限分别给出正确结果，不自动回退当前用户。
- A 用户慢读取后选择 B：A 的数据、异常和加载结束事件均不能覆盖 B；弹窗和重试也不能改写 B 的配置。
- 托管字段的名称、类型和结构受保护；类型控件不要求 JSON 知识；恢复默认保留其他字段；并发编辑返回可理解的冲突。
- 键有子键但无值、真正空键、读取失败、断线和锁定状态不会混为“没有值”。
- Windows / Linux、两种窗口样式、浅/深主题、中/英/日、窄窗口和键盘操作通过布局与行为验证。

实现须同步更新 Shared Protocol、Server、桌面全部调用者、测试和当前文档；本草案不表示功能已实现或测试已执行。
