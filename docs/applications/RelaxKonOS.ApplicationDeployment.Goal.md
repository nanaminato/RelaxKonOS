# RelaxKonOS 容器化应用部署 Goal

> 建立日期：2026-09-19
>
> 状态：目标与验收基线已建立，功能待实现；本文不表示已具备应用部署能力。
>
> 实现、测试执行、阻塞与证据统一记录于 [实施进度](./RelaxKonOS.ApplicationDeployment.Progress.md)。

## 1. 目标与完成条件

在现有 Docker 管理能力上建立应用部署领域，使用户通过镜像或程序包部署 Java、.NET、Python 应用。应用构建和运行不调用宿主机的 Java、Maven、Gradle、dotnet SDK 或 Python；所需工具来自容器镜像。RelaxKonOS Server 自身的运行依赖不属于这一限制。

本 Goal 的第一阶段完成条件：

- 镜像、Java JAR、.NET 发布包、Python 项目包均可从客户端完成创建、部署、查看状态和日志、停止、启动及重新部署。
- 应用定义、不可变发布版本与后台操作持久化；客户端断开不终止任务，Server 重启后任务不会永久停留在 Running。
- 支持配置、资源限制、持久化数据卷、明确的就绪判定及版本回滚；失败不能被报告为部署成功。
- 可选接入现有 WebServerManager 的 HTTP 反向代理与证书绑定；无 Web Server 时仍可完成应用部署。
- 在不安装上述应用语言工具链的 Linux 验收宿主上完成三种程序包及镜像部署测试；实现项与必需测试均有可复核证据。

## 2. 范围

第一阶段只管理 RelaxKonOS.Server 所在主机的单个 Docker Engine，支持 Linux 容器和单服务 Compose 项目。具体 OS、CPU 架构、Engine/Compose 版本以实际测试记录为准，不宣称未验证的平台支持。

输入包括现成镜像引用、可执行 JAR、.NET 发布目录归档和带依赖锁定信息的 Python 项目归档。Python 依赖在镜像构建时安装，启动时不安装依赖。.NET 发布包必须校验部署类型、目标运行时、OS/架构；Java 普通非可执行 JAR、自定义复杂 classpath、传统 WAR 部署不作为默认模板能力。

后续范围：Git/源码构建、Java/.NET 多阶段编译模板、多服务依赖、自动触发部署、自动切流、远程 Engine、Windows 容器及集群。它们不作为第一阶段关闭条件，也不能以“后续范围”推迟第一阶段的恢复、权限和测试。

Docker Engine 安装继续归属 [受管安装服务 Goal](../services/RelaxKonOS.InstallationServices.Goal.md)。镜像拉取、应用构建和发布属于应用部署操作，不伪装成宿主运行时安装任务。不得自动回退为宿主语言环境执行。

## 3. 现有基础与模块边界

可复用接口不等于本 Goal 已实现或通过测试：

- `RelaxKonOS.Server/Docker/IDockerEngineService.cs`：镜像拉取/构建、容器创建、生命周期、日志与统计。
- `RelaxKonOS.Server/Docker/IDockerComposeService.cs`：Compose 校验、部署及项目操作。
- [Docker 管理器](./RelaxKonOS.DockerManager.md)：底层资源管理入口。
- [WebServerManager](./RelaxKonOS.WebServerManager.Design.md)：可选站点与反向代理集成。

新增协议建议放在 `Shared/RelaxKonOS.Protocol/ApplicationDeployments/`，服务在 `RelaxKonOS.Server/ApplicationDeployments/`，客户端在 `Client/RelaxKonOS.Client/Apps/ApplicationDeployments/`。应用部署协调器组合现有 Docker 服务，语言模板只生成构建与启动定义，不各自复制容器管理引擎。

客户端只访问 Server，不直连 Docker socket、不保存镜像仓库凭据。调用 Docker 时使用结构化参数，不拼接 shell 命令。容器入口和参数使用数组表达，并按模板校验。

首个正式发布前遵循根目录 AGENTS.md：契约变更直接更新所有仓库调用方、测试、示例和文档，不保留旧路由、别名、双格式解析或兼容适配器。

## 4. 领域模型与协议

| 模型 | 必需信息 |
| --- | --- |
| Application | ID、名称、所有者/授权范围、部署来源类型、期望状态、当前版本、端口、资源限制、数据卷及可选站点关联 |
| ApplicationRevision | ID、应用 ID、模板版本、输入校验值、实际镜像 ID/digest、平台、入口、配置快照和密钥版本引用、创建时间 |
| DeploymentOperation | ID、应用/目标版本、操作类型、请求者、幂等引用、状态、阶段、可空进度、时间、稳定问题码、取消能力和恢复结果 |

镜像标签仅作输入与展示，发布版本绑定实际镜像身份；本机构建可记录 image ID，无 registry digest 时不得编造。容器为可替换实例，不能承担应用数据库的职责。密钥正文不得进入版本快照、操作账本或审计。

建议 API 基址 `/api/v1.0/application-deployments`：应用 CRUD、版本列表、部署/启停/回滚操作、操作查询与取消、日志读取。路由与 DTO 统一定义在 Protocol，变更请求严格校验未知字段、长度、端口、资源额度与目标引用。

长操作返回 `202 Accepted` 和 operation ID；查询支持重连恢复，实时事件仅用于通知，持久状态为权威来源。部署请求要求幂等键；同键不同请求必须冲突，同应用并发变更必须串行。首轮协议提交应冻结具体 DTO、路由、权限 ID 和问题码，并同步更新本文与进度记录。

## 5. 模板与输入处理

| 模板 | 构建内容 | 运行入口 |
| --- | --- | --- |
| Image | 拉取已有镜像，验证平台并记录实际身份 | 默认镜像入口；覆盖需显式配置 |
| JavaJar | 选定版本的 JRE 基础镜像与 JAR | `java -jar` 加受控参数 |
| DotNetPublish | 按框架依赖/自包含及 Web/Worker 选择基础镜像，复制发布文件 | `dotnet App.dll` 或自包含入口 |
| PythonProject | 选定 Python 镜像，安装锁定依赖，复制应用 | 用户指定模块或入口，不假定 Web 框架 |

模板具有版本和支持平台清单；基础镜像选择记录实际身份，不以浮动 latest 作为可复现依据。第一阶段不开放任意 Dockerfile 上传；Python 包构建依然可能执行代码，必须按授权和资源限制处理。

上传进入 Server 受限暂存区，使用绑定操作者的文件引用；限制压缩包大小、解压总量和文件数，拒绝路径穿越、越界链接及入口越界。仅将声明的文件放入构建上下文，排除凭据与无关宿主文件。构建缓存、暂存数据和镜像需有有界清理策略；不得清理其他应用或用户资源。

## 6. 发布、取消与恢复

操作状态：`Queued | Running | Succeeded | Failed | Cancelled | Interrupted`。

阶段至少包含：`Preflight → Preparing → Pulling/Building → Creating → HealthChecking → Activating → Completed`；清理与恢复使用明确阶段。进度只报告可靠的阶段内字节数/工作量，无可靠分母则为 null，不伪造累计百分比。

1. 预检 Engine、Compose、平台、授权、磁盘、端口与输入；缺依赖明确失败并引导安装，不自动改变宿主环境。
2. 拉取或构建镜像，持久化候选版本，给所有受管资源加应用、版本和操作标签。
3. 创建实例并等待有界就绪检查；HTTP 应用使用可配置 HTTP 检查，Worker 必须配置适合其工作负载的检查或明确显示仅进程存活级别。
4. 第一阶段允许停机替换，UI 必须显示策略；更新可选反向代理前验证配置，提交成功后记录当前版本。
5. 失败时尽力恢复旧实例与站点配置；恢复失败单独记录问题和需人工处理的状态，不覆盖原始错误或伪报成功。

Compose 不承担完整发布事务。每个外部副作用前后记录阶段和资源身份；Server 启动时根据账本、标签、真实容器及站点状态核对，结论不确定则标为 Interrupted，禁止盲目重复发布。取消发生在安全边界；进入激活/恢复临界区时返回不可取消，取消后清理候选资源但保留旧版本和数据。

回滚使用旧镜像与旧配置引用重新部署，先验证镜像、密钥版本和数据兼容性。数据库迁移及持久化数据变化不因镜像回滚而撤销；第一阶段不自动执行数据库迁移。数据卷默认不随应用/版本删除，显式删除须经过独立授权确认。

## 7. 运行、安全与访问入口

- 默认设置内存/CPU、日志轮转和重启策略；模板默认非 root，验证数据目录权限，不提供特权容器或 Docker socket 挂载。
- 默认使用受管命名卷；任意宿主目录挂载不进入第一阶段向导。密钥用受保护存储与最小范围文件挂载，构建凭据不得写入镜像层。
- 新增应用读取/管理权限并沿用现有授权体系；读取日志、取消任务、访问上传引用也检查资源权限。应用管理不能绕开 Docker 高权限边界。
- 操作日志与应用日志有访问控制、长度限制和脱敏；审计记录操作者、目标、结果、operation ID，不保存凭据或原始构建输出。
- 宿主代理通过回环地址映射端口访问容器；容器代理通过共同网络访问服务名，不能把容器内 localhost 当成宿主地址。无代理时明确选择绑定地址及开放端口。
- 对 Docker 管理器中受管资源的变更建立归属提示与冲突控制；发现外部删除/修改时显示漂移或缺失状态，不自动接管无标签资源。

## 8. 客户端与实施顺序

向导：部署来源 → 模板/版本 → 程序入口 → 端口/配置/数据卷/资源 → 可选域名与证书 → 部署预览 → 操作进度。

详情页展示当前版本、期望/实际状态、就绪检查级别、访问入口、日志、资源和历史操作；支持重连观察及明确的失败恢复入口。错误使用稳定问题码与三语本地化，不把 Docker 原始命令作为产品提示。

| 阶段 | 交付内容 | 测试门槛 |
| --- | --- | --- |
| M1 | Protocol、权限、模型、持久化与操作状态机 | T01–T03、T10 |
| M2 | 镜像部署、Compose 适配、资源归属与恢复 | T04、T08、T09、T11 |
| M3 | 受限上传、Java/.NET/Python 模板 | T05–T07、T10 |
| M4 | 客户端向导、日志、版本操作、可选站点 | T08、T12、T13 |
| M5 | 真实 Engine 验收、恢复演练和文档收口 | T14、T15，所有必需项复核 |

测试编号、编写状态、执行状态和证据见进度文档。每个阶段同时推进必要测试，不将编译通过视为验收通过。

## 9. Goal 关闭规则

第一阶段所有实施项完成，T01–T15 必需测试均通过，失败/阻塞已解决；有真实 Docker 环境下三种语言程序包与现成镜像的证据，并证明应用工具链未在宿主执行。未测平台明确保持未验证。

更新用户文档、帮助入口和本地化，记录验证提交、环境版本、命令和结果。仅有接口、模拟测试或成功的 `compose up` 不能关闭 Goal。后续范围另立任务，不计入第一阶段完成率。
