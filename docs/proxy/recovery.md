# 代理网络恢复

启动时，RelaxKonOS 会先评估任何持久化的 TUN 恢复标记，随后才允许再次激活。“紧急禁用 TUN”会独立于运行时卸载恢复已捕获的网络状态；若恢复失败，标记会保留。

Mihomo 直连重载失去确认时，组件中心的运行时恢复面板显示原操作 ID。具备管理权限并完成宿主提权的操作员可以重试。结果未知时，重试只在受保护的活动文件仍匹配候选摘要时恢复原磁盘配置。原操作仍显示待恢复，因为 Mihomo 可能继续运行已加载的候选配置。

如果档案发布已记录控制器确认，启动恢复或具名重试会核对候选文件并完成原档案提交。按原 ID 再次重试可读取已保存的回执。文件或档案身份发生变化时，恢复保持待处理。TUN 紧急禁用和系统代理恢复继续使用各自的持久记录。

活动订阅的排队刷新使用原刷新 ID 记录直连重载确认。启动恢复完成档案提交后，刷新回执和原幂等键仍指向同一次刷新。恢复沿用已转换的候选配置和原订阅时间，不重新下载订阅或重载控制器。如果 Server 在原控制器确认前退出，查询或再次提交时会根据匹配的发布检查点，将原队列记录保存为中断且等待发布恢复（`publication_pending`），完成时间留空。以原键重试返回同一条记录，新刷新继续受写入门禁限制。

排队激活使用原激活 ID 发布并恢复所选档案。重启后用原幂等键或操作 ID 可查询已确认的成功或失败。原发布尚未核实时，原回执保持 `publication_pending`，完成时间留空。恢复不会重新激活、下载订阅或更新抓取时间。

直连激活丢失重载应答时，磁盘可恢复到上次确认的配置，而运行中的 Mihomo 可能仍使用候选配置。原操作保持待恢复并阻止新激活。若控制器已明确拒绝候选且旧配置重载成功，原操作可按原 ID 读回失败结果。

批量刷新保留原批次 ID，并在队列台账记录各订阅的独立操作 ID。Server 中断后，查询或再次提交只核对已派发分项的原回执，未开始的分项记为跳过。没有可核对回执的分项会让原批次保持 `batch_pending`，完成时间留空。所有已派发分项得到确认后，原批次显示 `batch_interrupted`，表示批次中断且没有待核对的分项。原幂等键始终返回原批次，恢复期间不会重新下载、重载或启动跳过的分项。

刷新未激活的订阅时，Server 在替换草稿前保存原操作 ID、候选摘要和抓取时间。若文件已替换而 SQLite 回执尚未提交，恢复核对文件内的操作标记及完整摘要，只补交原回执和抓取时间。文件缺失、内容不匹配或档案身份改变时，原操作保持待恢复，相关档案的替换和激活会被拦截。

若替换没有发生，只有原草稿摘要和该操作的暂存文件都匹配，Server 才会保存清理决定并移除暂存文件，随后按原 ID 记录未应用。原草稿和订阅时间保留，恢复不重新下载，也不重新尝试替换。清理后回执写入中断时，可按原决定继续。清理决定前缺少暂存文件或任一内容发生漂移时，原操作继续待恢复。

如果直连设置已记录运行时和宿主的成功应答，且宿主代理策略前后一致，恢复会核对候选配置和设置文件并完成本地提交。结果仍未知或文件出现独立改动时，原操作继续待处理。

Linux 直连设置的宿主策略变更在收到运行时确认后，可按原 ID 核对 Helper 的历史回执和当前代理值。两者匹配且候选文件一致时，恢复完成本地设置提交。guard 需要独立维护已保存策略时，会保留原操作为待恢复，便于区分原变更和后续安全操作。

如果待恢复变更切换了监听端口，guard 恢复已保存的代理地址后，Mihomo 仍可能在候选端口运行。此时指向旧端口的新连接可能被拒绝，已有连接仍可能继续转发。恢复面板会保留原操作 ID 和待恢复状态。

对于 guard 已接管的 Linux 直连设置，具备管理权限并完成宿主提权的操作员可确认“恢复已保存代理策略”。应用会使用独立恢复 ID，核对旧监听和宿主代理效果。完成后原操作显示中断，并关联补偿 ID。TUN 安全责任尚未解除或文件漂移时，恢复仍待处理。补偿重载应答丢失后，再次确认原补偿可核对完整配置摘要和实际监听。只有可证明已恢复原端口、日志级别和 TUN 关闭，且候选监听已关闭时才继续原宿主补偿。证据不足时保留原补偿 ID 和待核验状态。

首次平台验证应在带有第二条管理连接的一次性 VM 上进行。尝试 Windows 或 Ubuntu 恢复演练前，请先查看跳过测试登记表。
